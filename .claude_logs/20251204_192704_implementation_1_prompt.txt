## Service Specification
# Service Specification: shortening-service

## Overview

The `shortening-service` is a high-performance URL shortening API service responsible for accepting long URLs, validating them, generating unique short codes, and persisting URL mappings to a PostgreSQL database. The service is designed to handle 1,000 requests per second with p99 latency under 200ms, implementing rate limiting and input sanitization to prevent abuse. It operates as a write-optimized service in a read-heavy architecture, where the companion `redirect-service` handles the majority of traffic.

## Tech Stack

- **Language:** Go 1.21+
- **Framework:** Chi v5 (lightweight HTTP router)
- **Database:** PostgreSQL 15 (Cloud SQL with High Availability)
- **Cache:** Redis 7.0 (Memorystore) - for rate limiting and optional cache invalidation
- **Container Runtime:** Cloud Run (serverless containers)
- **Libraries:**
  - `go-chi/chi/v5` - HTTP routing and middleware
  - `go-chi/cors` - CORS middleware
  - `jackc/pgx/v5` - PostgreSQL driver and connection pooling
  - `go-redis/redis/v9` - Redis client for rate limiting
  - `golang.org/x/time/rate` - Token bucket rate limiter
  - `google.golang.org/api/idtoken` - Future authentication support
  - `rs/zerolog` - Structured JSON logging
  - `prometheus/client_golang` - Metrics instrumentation

**Business Logic:**

**Happy Path:**
1. Request arrives with valid JSON body containing `url` field
2. Extract client IP from `X-Forwarded-For` header for rate limiting
3. Check rate limit: 100 requests per minute per IP address
4. Validate URL format:
   - Must start with `http://` or `https://`
   - Must be between 10 and 2048 characters
   - Must contain valid domain (basic DNS validation)
   - Must not contain dangerous schemes (javascript:, data:, file:)
5. Generate unique short code using Snowflake-inspired algorithm:
   - 41 bits: Timestamp (milliseconds since custom epoch)
   - 10 bits: Worker ID (derived from Cloud Run instance ID)
   - 12 bits: Sequence number (incremented for same millisecond)
   - Result: 63-bit integer encoded to Base62 (6-8 characters)
6. Insert URL mapping into PostgreSQL:
   - short_code (unique constraint ensures no collisions)
   - long_url
   - created_at (automatic timestamp)
   - created_by_ip (for abuse tracking)
7. Return 201 Created with shortened URL details
8. Log successful operation with structured logging
9. Increment Prometheus metrics: `shortening_requests_total{status="success"}`

**Sad Path - Validation Failures:**
1. Missing `url` field → Return 400 with `validation_error`
2. Empty `url` string → Return 400 with `validation_error`
3. URL too short (< 10 chars) → Return 400 with `validation_error`
4. URL too long (> 2048 chars) → Return 400 with `validation_error`
5. Invalid scheme (not http/https) → Return 400 with `invalid_url`
6. Malformed URL (no domain, invalid characters) → Return 400 with `invalid_url`
7. Dangerous schemes detected (javascript:, data:) → Return 400 with `invalid_url` and log security event
8. Rate limit exceeded → Return 429 with `Retry-After` header
9. Log validation failure with reason
10. Increment Prometheus metrics: `shortening_requests_total{status="validation_error"}`

**Sad Path - Database Failures:**
1. PostgreSQL connection pool exhausted → Return 503 with `service_unavailable`
2. Database connection timeout → Return 503 with `service_unavailable`
3. Unique constraint violation (collision, extremely rare) → Retry short code generation (max 3 attempts), then return 500
4. Database write timeout → Return 503 with `service_unavailable`
5. Log error with full context (request_id, error details)
6. Increment Prometheus metrics: `shortening_requests_total{status="database_error"}`
7. Trigger Cloud Monitoring alert if error rate exceeds threshold

**Edge Cases:**

1. **Duplicate URL Submission:**
   - Behavior: Generate new short code each time (no deduplication in MVP)
   - Rationale: Simplifies logic, avoids privacy concerns
   - Future: Optional deduplication with user accounts

2. **URL with Fragments:**
   - Example: `https://example.com/page#section`
   - Behavior: Store entire URL including fragment
   - Redirect service will preserve fragment

3. **URL with Special Characters:**
   - Example: `https://example.com/path?q=hello%20world&lang=en`
   - Behavior: Store URL as-provided (already encoded)
   - Validation: Ensure proper percent-encoding

4. **International Domain Names (IDN):**
   - Example: `https://münchen.de/path`
   - Behavior: Accept Punycode-encoded domains
   - Validation: Basic format check only

5. **Very Short URLs:**
   - Example: `https://t.co`
   - Behavior: Accept if >= 10 characters total
   - Rationale: Prevent abuse, ensure minimum URL validity

6. **URLs with Authentication:**
   - Example: `https://user:pass@example.com/path`
   - Behavior: Accept and store as-is
   - Security: Log warning (potential credential exposure)

7. **Localhost/Private IPs:**
   - Example: `http://localhost:8080` or `http://192.168.1.1`
   - Behavior: Accept (no DNS validation for MVP)
   - Future: Optional blocking of private IP ranges

8. **Concurrent Requests with Same URL:**
   - Behavior: Each request generates unique short code
   - Database: Handles concurrent writes with MVCC

9. **Short Code Collision (Theoretical):**
   - Probability: < 1 in 1 billion with 63-bit space
   - Handling: Retry generation up to 3 times
   - Fallback: Return 500 and alert engineering team

10. **Request with Extra Fields:**
    - Example: `{"url": "...", "custom_code": "abc"}`
    - Behavior: Ignore extra fields, process only `url`
    - Future: Support custom codes with authentication

## Short Code Generation Algorithm

### Snowflake-Inspired Distributed ID Generation

**Algorithm Overview:**

The service generates unique 63-bit integers using a Snowflake-inspired approach, then encodes them to Base62 for URL-friendly short codes.

**Bit Layout (63 bits total):**
```
┌─────────────────────────────────────────────────────────────┐
│  41 bits: Timestamp  │ 10 bits: Worker ID │ 12 bits: Sequence │
└─────────────────────────────────────────────────────────────┘
```

**Components:**

1. **Timestamp (41 bits):**
   - Milliseconds since custom epoch: 2024-01-01 00:00:00 UTC
   - Range: ~69 years from epoch
   - Ensures time-based ordering

2. **Worker ID (10 bits):**
   - Derived from Cloud Run instance metadata
   - Range: 0-1023 (supports 1024 concurrent instances)
   - Extracted from `CLOUD_RUN_INSTANCE_ID` environment variable
   - Fallback: Hash of hostname if env var unavailable

3. **Sequence (12 bits):**
   - Counter for IDs generated in same millisecond
   - Range: 0-4095 (4096 IDs per millisecond per worker)
   - Resets to 0 when timestamp increments
   - If sequence exhausted, wait for next millisecond

**Capacity:**
- **Per Worker:** 4,096 IDs per millisecond = 4,096,000 IDs per second
- **Total (1024 workers):** 4.2 billion IDs per second
- **Total Space:** 2^63 = 9.2 quintillion unique IDs

**Base62 Encoding:**

Character set: `0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`

```
63-bit integer → Base62 encode → 6-8 character string

Examples:
1234567890123 → "dnh5xN7"  (7 chars)
9876543210987 → "2BiIEk3"  (7 chars)
```

**Implementation Pseudocode:**

```go
type SnowflakeGenerator struct {
    workerID      uint16
    sequence      uint16
    lastTimestamp int64
    mutex         sync.Mutex
}

func (g *SnowflakeGenerator) Generate() (int64, error) {
    g.mutex.Lock()
    defer g.mutex.Unlock()
    
    timestamp := currentMillis() - EPOCH_OFFSET
    
    if timestamp < g.lastTimestamp {
        // Clock moved backwards
        return 0, ErrClockMovedBackwards
    }
    
    if timestamp == g.lastTimestamp {
        // Same millisecond - increment sequence
        g.sequence = (g.sequence + 1) & 0xFFF
        if g.sequence == 0 {
            // Sequence exhausted - wait for next millisecond
            timestamp = waitNextMillis(g.lastTimestamp)
        }
    } else {
        // New millisecond - reset sequence
        g.sequence = 0
    }
    
    g.lastTimestamp = timestamp
    
    // Combine components into 63-bit ID
    id := (timestamp << 22) | (int64(g.workerID) << 12) | int64(g.sequence)
    
    return id, nil
}

func Base62Encode(num int64) string {
    const charset = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
    if num == 0 {
        return "0"
    }
    
    result := ""
    for num > 0 {
        result = string(charset[num%62]) + result
        num /= 62
    }
    return result
}
```

**Collision Handling:**

1. **Primary Prevention:** Unique worker IDs and sequence numbers ensure no collisions
2. **Database Constraint:** `UNIQUE` constraint on `short_code` column
3. **Retry Logic:** If constraint violation occurs (extremely rare):
   - Regenerate new ID (max 3 attempts)
   - Log collision event for investigation
   - Return 500 error if all retries fail

**Edge Cases:**

1. **Clock Skew:**
   - If system clock moves backwards, reject ID generation
   - Return error and log critical alert
   - Prevent duplicate IDs from being generated

2. **Worker ID Collision:**
   - Multiple instances get same worker ID (misconfiguration)
   - Database constraint prevents duplicate short codes
   - Monitoring alerts on high constraint violation rate

3. **Sequence Exhaustion:**
   - More than 4096 requests in single millisecond on one worker
   - Generator waits for next millisecond (adds ~1ms latency)
   - Extremely rare with proper load balancing

## Rate Limiting Strategy

### Token Bucket Algorithm

**Configuration:**

```go
type RateLimitConfig struct {
    // Per-IP limits
    PerIPRate     int           // 100 requests
    PerIPBurst    int           // 120 requests (allows small bursts)
    PerIPWindow   time.Duration // 1 minute
    
    // Global limits
    GlobalRate    int           // 1000 requests
    GlobalBurst   int           // 1200 requests
    GlobalWindow  time.Duration // 1 second
}
```

**Implementation:**

**Storage:** Redis (Memorystore) with TTL-based keys

**Per-IP Rate Limiting:**
```
Redis Key: "ratelimit:ip:{ip_address}"
Redis Value: Token count (integer)
Redis TTL: 60 seconds

Algorithm:
1. GET current token count for IP
2. If key doesn't exist, initialize with max tokens (100)
3. If tokens > 0, decrement by 1 and allow request
4. If tokens == 0, reject with 429 Too Many Requests
5. Tokens refill at rate of 100 per minute (1.67 per second)
```

**Global Rate Limiting:**
```
Redis Key: "ratelimit:global"
Redis Value: Token count (integer)
Redis TTL: 1 second

Algorithm:
1. GET current global token count
2. If key doesn't exist, initialize with max tokens (1000)
3. If tokens > 0, decrement by 1 and allow request
4. If tokens == 0, reject with 429 Too Many Requests
5. Tokens refill at rate of 1000 per second
```

**Response Headers:**
```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 73
X-RateLimit-Reset: 1705315860
Retry-After: 47 (seconds until reset)
```

**Error Response (429):**
```json
{
  "error": "rate_limit_exceeded",
  "message": "Too many requests. Please try again later.",
  "retry_after": 47,
  "limit": 100,
  "window": "1 minute"
}
```

**Bypass Logic:**

```go
// Future: Allow authenticated requests to bypass rate limits
if request.HasValidAPIKey() {
    // Skip rate limit check
    return next(w, r)
}
```

**Monitoring:**
- Metric: `rate_limit_hits_total` (counter)
- Alert: If rate limit hits > 10% of total requests, investigate abuse
- Log: IP addresses that hit rate limit for abuse tracking

# Architecture: URL Shortener Service

## Goal

Design a high-performance, scalable URL shortening system that prioritizes low-latency redirects and reliable URL shortening. The architecture follows microservices principles with separate services for write operations (URL shortening) and read operations (redirects) to optimize for the read-heavy traffic pattern. The system leverages caching extensively to meet aggressive latency requirements and uses GCP managed services for scalability and reliability.

### Short Code Generation Algorithm

**Approach**: Snowflake-inspired distributed ID generation + Base62 encoding

```
Components:
- Timestamp (41 bits): Milliseconds since epoch
- Worker ID (10 bits): Cloud Run instance identifier
- Sequence (12 bits): Counter for same millisecond

Result: 63-bit unique integer → Base62 encode → 6-8 character string
```

**Base62 Character Set**: `0-9a-zA-Z` (62 characters)

    created_by_ip INET,
    
    -- Indexes
    CONSTRAINT short_code_length CHECK (char_length(short_code) BETWEEN 6 AND 8)
);

CREATE INDEX idx_short_code ON url_mappings(short_code);
CREATE INDEX idx_created_at ON url_mappings(created_at DESC);

### Caching Strategy

**Cache Structure** (Redis):
```
Key: "url:{shortCode}"
Value: "{longUrl}"
TTL: 3600 seconds (1 hour)
```

**Cache-Aside Pattern**:
1. Check Redis for `url:{shortCode}`
2. If found (cache hit): Return URL and redirect
3. If not found (cache miss):
   - Query PostgreSQL read replica
   - If found: Store in Redis with TTL, then redirect
   - If not found: Return 404

**Cache Warming**: Most popular URLs stay cached due to access frequency

**Cache Invalidation**: Handled by shortening-service (not required for current scope)

### Read Flow Optimization

```
Request → Parse shortCode (0.1ms)
       → Redis GET (1-2ms typical)
       → [Cache Hit 95%+] → Redirect (total: ~3-5ms)
       → [Cache Miss 5%-] → PostgreSQL Query (5-10ms)
                          → Redis SET (1-2ms)
                          → Redirect (total: ~15-20ms)
```

## Product Requirements
# PRD: URL Shortener Service

## Problem Statement

Long URLs are difficult to share, remember, and use in contexts with character limits (SMS, social media, print materials). Users need a simple, fast way to convert lengthy URLs into short, manageable links that reliably redirect to the original destination. This problem affects marketers, developers, content creators, and everyday users who frequently share links.

## Goals & Success Metrics

- Goal 1: Enable fast and reliable URL shortening
  - Metric: 99th percentile API response time < 100ms for shortening requests
- Goal 2: Provide instant and reliable redirects
  - Metric: 99th percentile redirect latency < 50ms
- Goal 3: Ensure high system availability
  - Metric: 99.9% uptime for redirect service

## Target Users

### Persona 1: Developer

- Characteristics: Integrates URL shortening into applications via API, values simplicity and reliability
- Pain points: Complex APIs, poor documentation, unreliable services, slow response times

### Persona 2: End User

- Characteristics: Needs to shorten URLs for sharing via messaging or social platforms
- Pain points: Long URLs that break in messages, hard to remember links, slow redirect times

## User Stories

### US-001: Shorten a URL

As a user, I want to submit a long URL so that I receive a shortened URL I can share.

**Acceptance Criteria:**

- [ ] System accepts a valid URL via API
- [ ] System returns a unique short code
- [ ] System returns the complete shortened URL
- [ ] Response time is under 200ms

### US-002: Redirect to Original URL

As a user, I want to access a shortened URL so that I am redirected to the original destination.

**Acceptance Criteria:**

- [ ] System accepts short code in URL path
- [ ] System performs HTTP 301/302 redirect to original URL
- [ ] Redirect happens within 100ms
- [ ] Invalid short codes return 404 error

### US-003: Validate Input URL

As a system, I want to validate submitted URLs so that only properly formatted URLs are shortened.

**Acceptance Criteria:**

- [ ] System rejects malformed URLs
- [ ] System rejects empty inputs
- [ ] System returns appropriate error messages

## Functional Requirements

### FR-001: URL Shortening API

The system shall provide an API endpoint that accepts a long URL and returns a shortened URL with a unique short code (6-8 alphanumeric characters).

### FR-002: URL Redirect

The system shall redirect requests to shortened URLs (via short code) to the original long URL using HTTP 301 (permanent) redirect.

### FR-003: URL Validation

The system shall validate that submitted URLs are properly formatted with a valid scheme (http/https) before processing.

### FR-004: Short Code Generation

The system shall generate unique, collision-free short codes using base62 encoding or similar algorithm.

### FR-005: Persistent Storage

The system shall store URL mappings (short code → long URL) in a persistent data store.

## Non-Functional Requirements

### Performance

- URL shortening requests must complete in < 200ms (p99)
- Redirect requests must complete in < 50ms (p99)
- System must handle 1,000 shortening requests per second
- System must handle 10,000 redirect requests per second

### Scalability

- System must scale horizontally to handle increased load
- Database must support sharding for future growth

### Security

- Input URLs must be sanitized to prevent injection attacks
- Rate limiting must be implemented to prevent abuse
- HTTPS must be enforced for all API endpoints

### Availability

- System must maintain 99.9% uptime
- Redirect service must have higher priority than shortening service during degradation

## Scope

### In Scope

- REST API for URL shortening
- HTTP redirect service
- URL validation
- Short code generation
- Persistent storage of URL mappings

### Out of Scope

- User authentication/accounts
- Analytics and click tracking
- Custom short codes/aliases
- Link expiration
- QR code generation
- Web UI/frontend

## Dependencies & Integrations

- Database system (PostgreSQL, Redis, or similar)
- Load balancer for traffic distribution
- DNS configuration for short domain

## Assumptions & Constraints

### Assumptions

- Short domain has been acquired and configured
- Infrastructure (servers, database) is available
- Traffic will be primarily read-heavy (more redirects than shortening)

### Constraints

- Short codes limited to 6-8 characters
- Only http:// and https:// URLs supported
- No support for URL modification after creation

## Risks & Mitigations

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| Short code collision | High | Low | Use proven unique ID generation (Snowflake, UUID-based) |
| Database failure | High | Low | Implement read replicas and caching layer |
| Abuse/spam | Medium | Medium | Implement rate limiting and URL blacklisting |
| High redirect latency | Medium | Medium | Use in-memory caching (Redis) for hot URLs |

- [ ] Redirect service functional and tested
- [ ] Performance benchmarks met (latency, throughput)
- [ ] Database persistence verified
- [ ] Error handling implemented for edge cases
- [ ] Load testing completed successfully
